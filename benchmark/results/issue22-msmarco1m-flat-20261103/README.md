# Issue #22 phase 1, flat: MS MARCO-1M, real vs doc queries, equal memory and equal recall (Hartmut, 2026-11-03)

Runs 2 and 4 of #22 phase 1: TieredQ (fast mode, #13 defaults: nibble scoring, automatic 6-bit cap, flat range
pruning) against RaBitQ and Qdrant TQ+, flat exhaustive search, at 1/2/4 bits/dim. Tables: [report-tables.md](report-tables.md),
generated by [`experiments/issue22_flat/report_tables.py`](../../experiments/issue22_flat/report_tables.py).
Workspace: `~/experiments/TieredQ-issue22-flat-20261103` (tree `source` = `5ba9a22` + `source-changes.patch`, the
harness changes committed with this bundle). Host: i9-7980XE (AVX-512, no VNNI), 36 CPUs, 62 GB, shared.

## Data
`msmarco1m` / `msmarco1m-doc` from [msmarco1m_data.py](../../msmarco1m_data.py), the cache of
[issue22-msmarco1m-20261031](../issue22-msmarco1m-20261031/): Cohere embed-english-v3.0 (1,024-d), 1,000,000
passages, two query sets on one base: `real` (1,000 MS MARCO dev questions) and `doc` (1,000 held-out passages, the
DBpedia setup). Exact FP32 inner-product truth.

## Method
- **Equal memory** ([`job_flat.sh`](job_flat.sh) step 1): `match_memory.py --quick --datasets msmarco1m`, RaBitQ then
  `--reference qdrant`, seeds 0-2, one lane and output directory per bits/dim (CPUs 8-15 / 16-23 / 24-31). Each cell
  builds and reloads one index and scores **both** query sets on it (`companion_recall10`, after all memory reads), so
  one match yields both recalls; budgets are selected on storage only. Reference cells were measured fresh here.
- **Equal recall** (step 2): `equal_recall.py` per query set: the smallest TieredQ budget (8 code-bit resolution,
  bisected on seed-0 R@10) reaching each reference's mean R@10 on that set. For RaBitQ 4-bit on `real` the bisected
  2,362 code bits reach 0.9557 mean (seed 0 0.9585) against 0.9571, so [`job_extra_b4.sh`](job_extra_b4.sh) steps
  up in 8-bit steps until the seed mean reaches it: 2,378 code bits, 0.9578 mean (`equal-recall/b4/equal-recall-msmarco1m-mean.csv`);
  the tables use that budget.
- **Timing** (step 3): `run.py`, seed 0, threads 1/8 × batch 1/32, alone on CPUs 0-7 after all lanes finished (their
  SMT siblings 18-25 idle), interleaved on one tree: per bits/dim the reference, TieredQ at every matched and
  equal-recall budget, the other reference; real queries first, then doc. References are timed on both query sets.
  Two long-running unpinned services shared the host (`timing/host-processes.txt`).
- Equal-recall speed is shown against the reference cell that set the level and against the reference's **fastest**
  bits/dim whose mean recall reaches it ("vs fastest ref").
- The race between parallel `build_native` calls (#4 1M `lane_b2.sh`) hit the first launch; `native_build.py` now
  holds a lock around overlay patching and the CMake build (the aborted run's logs are not part of this bundle).

## Findings
**1. The real-query gain holds and is larger than the doc-query gain.** Δ R@10 at equal measured disk, mean of seeds
0-2 (RAM and peak in report-tables.md agree within 0.9 pt):

| Reference | bits/dim | Ref R@10 real | Δ real | Ref R@10 doc | Δ doc | real / doc gain |
|---|---:|---:|---:|---:|---:|---:|
| RaBitQ | 1 | 0.7619 | **+10.1 pt** | 0.8087 | +8.2 pt | 1.23 |
| RaBitQ | 2 | 0.8727 | **+7.6** | 0.8978 | +6.0 | 1.26 |
| RaBitQ | 4 | 0.9571 | **+2.6** | 0.9641 | +2.1 | 1.21 |
| Qdrant TQ+ | 1 | 0.7554 | **+9.9** | 0.8067 | +8.0 | 1.24 |
| Qdrant TQ+ | 2 | 0.8721 | **+7.2** | 0.9003 | +5.5 | 1.32 |
| Qdrant TQ+ | 4 | 0.9615 | **+2.1** | 0.9668 | +1.9 | 1.10 |

Real questions are harder for every codec (references lose 0.5-4.7 pt against doc queries), and TieredQ loses less.

**2. At equal recall TieredQ stores 0.53-0.63× the bits of either reference, on both query sets.** Throughput per
core (1t·b32) against RaBitQ: 3.0× at its 1-bit recall, 1.9× at 2-bit, 1.0× at 4-bit; against TQ+ 5-13×.
Single-query p50 against RaBitQ: 0.54× at 1 bit, 0.93× at 2, **1.8× slower at 4**. RaBitQ's speed is flat over 1-4
bits/dim (bound pruning keeps its extra bits off the hot path), so its fastest config at each level is within 3% of
the matching one. Real queries, seed 0:

| Reference level | TieredQ code bits | Stored bits TQ / ref | QPS 8t·b32 | QPS 1t·b32 | p50 1t·b1 |
|---|---:|---|---|---|---|
| RaBitQ 1-bit (0.7619) | 602 | 664 / 1,120 (0.59×) | 1,702 / 557 (3.06×) | 229 / 75 (3.05×) | 7.05 / 13.05 ms (0.54×) |
| RaBitQ 2-bit (0.8727) | 1,114 | 1,178 / 2,208 (0.53×) | 1,077 / 559 (1.93×) | 144 / 76 (1.89×) | 12.45 / 13.44 ms (0.93×) |
| RaBitQ 4-bit (0.9571) | 2,378 | 2,438 / 4,256 (0.57×) | 571 / 571 (1.00×) | 78 / 75 (1.04×) | 24.09 / 13.29 ms (**1.81×**) |
| TQ+ 1-bit (0.7554) | 594 | 655 / 1,088 (0.60×) | 1,753 / 143 (12.3×) | 232 / 18 (12.6×) | 6.93 / 53.72 ms (0.13×) |
| TQ+ 2-bit (0.8721) | 1,114 | 1,178 / 2,112 (0.56×) | 1,077 / 131 (8.3×) | 144 / 17 (8.7×) | 12.45 / 60.26 ms (0.21×) |
| TQ+ 4-bit (0.9615) | 2,570 | 2,630 / 4,160 (0.63×) | 532 / 114 (4.7×) | 72 / 14 (5.0×) | 26.68 / 70.24 ms (0.38×) |

Doc queries give the same ratios within about 3% (report-tables.md): flat speed does not depend on the query set.

**3. At equal memory TieredQ is faster than RaBitQ at 1 bit and slower from 2 bits up.** RAM-matched, real queries:
QPS 8t·b32 1.98× / 1.13× / **0.61×** and p50 0.94× / **1.68×** / **3.2×** at 1 / 2 / 4 bits/dim; against TQ+ 3.2-7.5×
faster everywhere. TieredQ's scan cost grows with its budget (1,100 → 635 → 350 QPS at about 1.1K / 2.2K / 4.2K code
bits); RaBitQ's does not. At 4 bits/dim the plain index trades its +2.6 pt for latency; at equal recall it keeps
RaBitQ's throughput with 43% less memory. `TieredQNestedIndex` (#13) is the 4-bit single-query path and was not timed here.

**4. Build at 1M** (8 threads; time from the timing cells, peak = RSS growth over the loaded FP32 corpus from the
match cells, seed 0, at the RAM-matched TieredQ budget):

| bits/dim | Build s TQ / RaBitQ | Build s TQ / TQ+ | Peak bits/vec TQ / RaBitQ | Peak bits/vec TQ / TQ+ |
|---:|---|---|---|---|
| 1 | 8.1 / 0.8 (10×) | 8.0 / 21.3 (0.37×) | 1,614 / 1,132 (1.43×) | 1,575 / 2,346 (0.67×) |
| 2 | 12.5 / 16.4 (0.76×) | 12.8 / 27.1 (0.47×) | 2,712 / 2,222 (1.22×) | 2,611 / 4,385 (0.60×) |
| 4 | 21.7 / 28.7 (0.76×) | 21.1 / 35.5 (0.59×) | 4,836 / 4,270 (1.13×) | 4,731 / 8,499 (0.56×) |

TieredQ's build peak is 0.5-0.6K bits/vector above its index (192-576 MiB at 1M), against about 50K bits/vector on
OpenAI-1536 100K in the #19 baseline. RaBitQ's 1-bit build is near free; TieredQ builds faster than both references
from 2 bits/dim up. At its equal-recall budgets TieredQ builds in 5.8 s (1 bit), 8.2 s (2) and 13.4-14.5 s (4).

## Decision gates (#22)
- **Gate 1 passes:** the `real` gain is 110-132% of the `doc` gain at equal disk (threshold ≥ ~70%), and at equal
  recall TieredQ needs 37-47% less RAM without losing QPS per core (1t·b32 ≥ 1.0× against both references at every
  level). Caveat for the write-up: single-query latency at RaBitQ's 4-bit recall is 1.8× RaBitQ's on the plain index.
- **Gate 2 (real gain collapses):** not triggered; query-aware allocation stays a no-go (#22, issue22-query-alloc).
- Gate 3 (rerank k′) is answered by the IVF + rerank bundles (issue22-msmarco1m-20261031, issue22-ssd-20261103).
